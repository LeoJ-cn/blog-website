## 二、技术原理与横向对比说明

# 城市智慧巡检 GIS 项目技术分析与选型对比

## 1. 为什么选择 Vue 3 + TypeScript + Pinia + OpenLayers

| 技术 | 当前项目中的职责 | 可选方案 | 选择当前方案的原因 |
|---|---|---|---|
| Vue 3 | 页面、面板、筛选、表单和响应式联动 | React、原生 JavaScript | 项目整体技术栈统一使用 Vue 3；Composition API 适合组织地图页面中大量相互关联的业务状态 |
| TypeScript | 约束事件、区域、轨迹、图层 ID、状态机和回调协议 | JavaScript | GIS 中经纬度、投影坐标、时间戳和几何类型容易混淆，静态类型可以提前暴露参数和协议错误 |
| Pinia | 保存事件、筛选条件、选中 ID、区域结果等业务状态 | provide/inject、组件局部状态、Vuex | 比 Vuex 更轻量且类型推导更直接；比全部放在组件中更便于跨面板共享状态 |
| OpenLayers | 地图、矢量图层、空间交互、投影转换和轨迹渲染 | Leaflet、Mapbox GL JS、Cesium | OpenLayers 原生支持 VectorSource、Cluster、Draw、Modify、投影转换及空间查询，适合二维政务 GIS 和复杂矢量交互 |
| Vite | 开发和生产构建 | Webpack | 当前项目默认构建链路；开发启动和模块更新较快。仓库仍保留 Webpack，但本 GIS 开发默认不执行 Webpack |

### OpenLayers 与其他地图方案的横向对比

| 方案 | 优点 | 局限 | 是否适合当前项目 |
|---|---|---|---|
| OpenLayers | 二维 GIS 能力完整；支持多种投影、矢量数据、Draw/Modify、Cluster 和空间查询 | API 较底层，需要自行管理对象和生命周期 | 最适合当前二维城市巡检场景 |
| Leaflet | 轻量、简单、上手快 | 复杂矢量交互、投影和海量数据能力通常依赖插件 | 适合简单标点地图，但当前空间交互较多 |
| Mapbox GL JS / MapLibre GL | WebGL 渲染和矢量瓦片能力强，适合超大规模可视化 | 样式体系和数据管线更复杂；Mapbox 还涉及 Token 和服务授权 | 若未来采用矢量瓦片或服务端切片，可以考虑 |
| Cesium | 三维地球、倾斜摄影和时空可视化能力强 | 二维业务系统使用成本和资源开销偏高 | 当前没有三维需求，属于过度设计 |

当前项目选择 OpenLayers，不是因为它在所有场景下性能最好，而是因为它同时覆盖二维地图、投影转换、矢量图层、空间绘制和几何判断，和城市巡检业务匹配度更高。

## 2. 地图数据源为什么这样选择

### 2.1 底图数据源

当前源码使用 OpenLayers 原生 `WMTS` Source 与 `WMTSTileGrid` 加载天地图墨卡托矢量底图 `vec_w` 和中文矢量注记 `cva_w`，显式配置 EPSG:3857 的矩阵集、分辨率和矩阵编号，并将两层组合为统一的基础图层组：

```ts
new LayerGroup({
  layers: [createTiandituTileLayer('vec'), createTiandituTileLayer('cva')],
})
```

| 数据源 | 优点 | 局限 | 当前选择 |
|---|---|---|---|
| OpenStreetMap | 无需商业 Token，接入简单，适合公开技术 Demo | 依赖公网；面向国内政务项目时数据来源和展示语境匹配度较弱 | 当前未使用 |
| 高德/百度地图 | 国内道路和 POI 数据更贴合国内用户 | 坐标体系涉及 GCJ-02/BD-09，接入通常需要 Key，并受服务条款限制 | 当前未使用 |
| 天地图 | 数据来源和表达更贴近国内政务 GIS；墨卡托服务可直接衔接 OpenLayers 默认 View | 需要浏览器端 Token、域名白名单和在线服务配额 | 当前 Demo 使用 `vec_w + cva_w` |
| 自建 XYZ/WMS/WMTS | 数据、样式和可用性可控，适合内网 | 需要地图服务器、切片和运维能力 | 当前 GitHub Pages 项目没有服务器 |
| 矢量瓦片 | 支持客户端动态样式，适合更大规模空间数据 | 制作、发布和渲染链路更复杂 | 当前事件数据仍采用前端 VectorSource |

选择天地图的主要原因是当前项目面向城市智慧巡检和政务 GIS 场景，底图来源及中文地理注记与项目语境更一致。项目使用浏览器端 Token 直接请求在线瓦片，仍可部署在 GitHub Pages；Token 通过本地环境变量和 GitHub Actions Secret 注入，并依靠域名白名单限制使用范围。

如果这是实际政务生产项目，通常需要根据内网部署、数据合规和服务授权，改为天地图、政务专网地图或自建 WMTS 服务。

### 2.2 业务事件数据源

当前业务数据不是来自后端接口，而是由固定种子的 Mock 数据生成器创建，支持 1k、10k、50k 和 100k 四种数据量。

| 方案 | 特点 | 当前是否使用 |
|---|---|---|
| 随机 Mock 数据 | 每次刷新数据不同，不容易复现问题 | 未使用 |
| 固定 seed Mock 数据 | 相同数量生成相同点位和状态，便于复现问题及观察优化效果 | 已使用 |
| 静态 JSON 文件 | 实现简单，但大文件会增加下载和解析成本 | 未使用 |
| IndexedDB | 可以跨刷新保存用户新增和修改数据 | 通用 Package 正在开发，尚未接入 GIS |
| HTTP 后端接口 | 能实现真实查询、权限、持久化和多人协作 | 当前 GitHub Pages 环境未接入 |

固定 seed 的优势是可复现，不代表这些数据来自真实生产环境。简历或面试中应明确称为“确定性 Mock 数据”。

## 3. 为什么需要 MapManager 分层

OpenLayers 是命令式、有状态的对象系统，Vue 是声明式、响应式的 UI 框架。

如果在 Vue 组件中直接创建和操作所有 OpenLayers 对象，会出现：

- Map 初始化和销毁逻辑散落；
- watch 重复触发时可能重复创建 Feature 或 Interaction；
- Map、Source 和 Layer 容易被 Vue 深层代理；
- 组件卸载后监听器和动画不容易完全释放；
- 业务组件需要了解大量 OpenLayers API。

因此项目将职责拆分为：

```text
GisManagementDemo.vue
├── 页面布局、表单和业务流程
├── Pinia：可序列化业务状态
└── MapManager：地图能力门面
    ├── LayerManager：图层所有权
    ├── SpatialInteractionManager：Select/Draw/Modify
    └── TrackPlaybackController：轨迹动画
```

### 横向对比

| 架构方式 | 优点 | 问题 |
|---|---|---|
| 全部写在 Vue 组件中 | 初期开发直接 | 文件快速膨胀，地图生命周期与页面业务耦合 |
| 将 OpenLayers 对象放入 Pinia | 多组件可以直接访问 | 对象包含复杂原型、缓存和循环引用，不适合序列化及响应式代理 |
| 使用 Vue composable 包装全部能力 | 符合 Vue 使用习惯 | 如果仍在 composable 中直接暴露 Map/Feature，边界问题依然存在 |
| 普通 TypeScript Manager | 生命周期清晰，不依赖 Vue，可稳定控制对象身份 | 需要设计明确的业务方法和回调协议 |

当前选择普通 TypeScript Manager，是因为地图对象本身并不是业务状态。Pinia 只保存 `eventId`、筛选条件和普通对象，地图层通过回调和业务 ID 与 Vue 通信。

## 4. 为什么采用 Layer、Source、Feature 分层

OpenLayers 中三个概念的职责不同：

- `Feature`：单个空间对象，例如一个巡检事件；
- `Source`：保存和查询一组 Feature；
- `Layer`：决定 Source 如何渲染及是否显示。

项目中的核心图层包括：

- BaseLayer：天地图 `vec_w` 矢量底图与 `cva_w` 中文注记图层组；
- EventLayer：普通事件点；
- ClusterLayer：聚合点；
- HeatmapLayer：风险热力；
- ResponsibilityGridLayer：责任网格；
- RegionLayer：用户绘制区域；
- TrackLayer：轨迹和人员位置；
- SelectionLayer：选中高亮；
- EventDraftLayer：事件编辑临时点位。

普通事件、Cluster 和 Heatmap 共享同一个事件 Source：

```ts
createEventLayer(eventSource)
createClusterLayer(eventSource)
createHeatmapLayer(eventSource)
```

### 共享 Source 与复制 Source 对比

| 方式 | 优点 | 问题 |
|---|---|---|
| 每个 Layer 使用独立 Source | 图层完全隔离 | 同一事件会创建多份 Feature，更新时容易不同步 |
| 多个 Layer 共享 Source | 只有一份事件 Feature，切换渲染方式无需复制数据 | 需要保证各 Layer 只负责渲染，不随意修改共享 Feature |
| 所有内容放在单个 Layer | 对象数量少 | 样式、显隐、交互和 zIndex 逻辑会高度耦合 |

项目选择共享 Source、拆分 Layer，在数据复用和展示职责之间取得平衡。

## 5. 为什么使用 Cluster 聚合

Cluster 根据当前地图分辨率，将屏幕上距离较近的事件合并为聚合点。

当前参数：

```ts
new ClusterSource({
  distance: 42,
  minDistance: 18,
  source: eventSource,
})
```

需要注意：Cluster 不会减少原始业务数据，它降低的是同一帧实际绘制和参与命中检测的图形数量。

### 横向对比

| 方案 | 优点 | 局限 |
|---|---|---|
| 普通 VectorLayer | 可直接选择每个点，业务关系简单 | 低 Zoom 下大量点重叠，绘制压力较大 |
| Cluster | 接入成本低，保留原始 Feature，适合浏览和逐层下钻 | 聚合计算仍在前端，极大规模数据仍受主线程限制 |
| Heatmap | 适合观察事件密度和风险分布 | 无法直接表示单个事件详情 |
| WebGL Points | GPU 渲染能力更强 | 样式、交互和兼容处理更复杂 |
| 矢量瓦片 | 适合更大规模数据和服务端分片 | 需要瓦片生产与发布服务 |
| 服务端聚合 | 浏览器只接收聚合结果 | 需要真实后端和聚合接口 |

当前项目需要同时演示单点操作和海量点浏览，因此提供普通点与 Cluster 两种互斥模式，Heatmap 作为独立分析视图。

## 6. 为什么需要视口 BBOX 加载

如果把十万条数据全部放入 Pinia 和 VectorSource，即使地图最终只显示其中一小部分，也要承担：

- 数据生成和转换成本；
- Vue 响应式管理成本；
- Feature 创建成本；
- VectorSource 空间索引构建成本；
- 地图绘制和命中检测成本。

当前实现只把视口范围内的数据放入 Pinia 和地图 Source：

```text
moveend
→ 计算 extent
→ 转换为 WGS84 BBOX
→ 查询视口数据
→ 更新 Pinia
→ Diff 同步 VectorSource
```

### 全量加载与视口加载对比

| 方案 | 优点 | 局限 |
|---|---|---|
| 全量加载 | 逻辑简单，地图移动不需要重新查询 | 数据量增大后初始化、内存和绘制成本上升 |
| 视口 BBOX 加载 | 地图只处理当前需要的数据，适合后续替换为后端空间查询 | 地图移动会产生频繁请求，需要处理竞态和缓存 |
| 矢量瓦片 | 天然按瓦片加载，适合超大规模空间数据 | 后端和数据发布链路复杂 |
| 分页接口 | 适合普通列表 | 不适合地图空间范围，页码与地图区域没有自然关系 |

当前项目选择 BBOX，是因为它与地图视口具有直接空间对应关系，也方便未来把 Mock Service 替换成后端空间查询接口。

## 7. 为什么使用固定网格空间索引

空间索引以 `0.01` 经纬度为默认网格边长，根据坐标计算网格编号：

```ts
Math.floor(coordinate / cellSizeDegrees)
```

BBOX 查询只读取覆盖网格中的候选事件，然后执行精确过滤。

### 横向对比

| 索引方案 | 优点 | 局限 |
|---|---|---|
| 全数组扫描 | 实现最简单 | 每次查询复杂度随完整数据量增长 |
| 固定网格 | 实现简单、构建快，适合分布范围相对稳定的点数据 | 数据极度不均匀时，热点网格可能包含大量候选 |
| R-Tree | 对不规则空间对象和范围查询更通用 | 实现、更新和维护成本更高 |
| Quadtree | 可根据空间密度递归划分 | 节点维护和动态更新更复杂 |
| Geohash | Key 可用于缓存和服务端分片 | 边界查询可能需要计算多个相邻区域 |
| PostGIS 空间索引 | 查询能力强，适合真实服务端 GIS | 当前项目没有服务器和空间数据库 |

固定网格不是通用最优解。当前 Mock 数据集中在一个城市范围，以点数据和矩形视口查询为主，因此固定网格已经能够展示空间索引思路，同时保持实现可解释。

## 8. 为什么使用量化 BBOX 和 LRU 缓存

地图轻微拖动会产生大量相近但不完全相同的 BBOX。如果直接以原始浮点坐标作为缓存 Key，缓存命中率会很低。

项目把最小边向外取整、最大边向外扩展到网格边界。相邻视口可以复用同一份候选结果，再按真实 BBOX 进行精筛。

LRU 缓存最大保存 20 条查询，避免缓存无限增长。

### 横向对比

| 缓存策略 | 优点 | 局限 |
|---|---|---|
| 不缓存 | 数据永远最新 | 重复拖动会重复计算相同区域 |
| 原始 BBOX 缓存 | 实现简单 | 浮点坐标稍有不同就无法命中 |
| 量化 BBOX 缓存 | 提高相邻视口复用率 | 命中结果范围更大，必须再次精确过滤 |
| 无限 Map 缓存 | 不会主动淘汰 | 长时间操作会持续占用内存 |
| LRU | 保留近期热点区域，容量可控 | 需要维护访问顺序 |
| TTL | 可以控制数据新鲜度 | 不能保证缓存容量稳定 |

当前 Mock 数据不会实时变化，因此主要使用 LRU 控制容量。未来接入后端后，可以根据业务实时性增加 TTL 或数据版本机制。

## 9. 为什么 AbortController、requestId 和数据版本要同时使用

| 机制 | 解决的问题 |
|---|---|
| AbortController | 尽早终止旧请求，减少无用计算和等待 |
| requestId | 防止较早发起但较晚返回的请求覆盖最新结果 |
| datasetVersion | 防止数据源已经切换后，旧数据集结果写入新数据集 |
| 参数快照 | 防止查询过程中筛选对象被外部修改 |

只使用 AbortController 不足以完全保证正确性，因为请求可能已经完成，或者旧回调已经进入任务队列。

只使用 requestId 可以保证结果正确，但旧请求仍会继续消耗资源。

因此当前实现同时使用取消机制和提交校验：AbortController 负责减少浪费，requestId 和 datasetVersion 负责最终一致性。

## 10. 为什么使用 Feature Diff 增量更新

视口结果变化后，可以有两种更新方式：

### 全量替换

```ts
source.clear()
source.addFeatures(newFeatures)
```

优点是简单，缺点是所有 Feature 对象都失效，选中态、空间索引和渲染状态需要重建。

### ID Diff

当前实现按事件 ID 分为：

- added；
- updated；
- removed；
- unchanged。

未变化 Feature 保留对象身份；发生变化的 Feature 就地更新属性和 Geometry。

| 更新方式 | 优点 | 局限 |
|---|---|---|
| 全量替换 | 实现简单，适合数据集整体切换 | 重复创建对象和重建 Source 索引 |
| ID Diff | 只处理真实变化，保留 Feature 身份 | 需要稳定唯一 ID 和字段比较逻辑 |
| 不可变 Feature 全量重建 | 数据流容易推导 | 对 OpenLayers 这类命令式对象系统成本较高 |
| 服务端增量推送 | 可以只传输变化数据 | 需要 WebSocket/SSE 和后端事件协议 |

项目在切换完整数据集时允许全量替换，在普通视口更新时使用 ID Diff，两者分别服务于不同场景。

## 11. 为什么使用样式缓存

OpenLayers Style 函数会在地图渲染过程中高频调用。

如果每次回调都创建新的 `Style`、`Fill`、`Stroke` 和 `Text`，会产生大量短生命周期对象和垃圾回收压力。

当前实现：

- 事件 Style 按处置状态缓存；
- Cluster Style 按聚合数量缓存；
- 轨迹节点 Style 按状态和标签缓存；
- Cluster 缓存设置 2048 上限。

### 横向对比

| 方案 | 优点 | 局限 |
|---|---|---|
| 每次创建 Style | 编写直观 | 高频重绘时产生大量临时对象 |
| 全局固定 Style | 性能稳定 | 无法表达不同状态和数量 |
| 按业务维度缓存 | 兼顾动态样式与实例复用 | 必须控制高基数 Key 导致的缓存增长 |
| Canvas 自定义绘制 | 控制能力强 | 实现和维护成本更高 |
| WebGL Shader | GPU 性能更好 | 开发、调试和交互逻辑更复杂 |

## 12. 为什么空间圈选采用粗筛加精筛

Polygon 和 Circle 查询分两步：

```ts
eventSource.forEachFeatureInExtent(geometry.getExtent(), (feature) => {
  const coordinate = feature.getGeometry()?.getCoordinates()

  if (coordinate && geometry.intersectsCoordinate(coordinate)) {
    eventIds.push(String(feature.getId()))
  }
})
```

### 横向对比

| 方法 | 正确性 | 性能 |
|---|---|---|
| 遍历全部事件并精确判断 | 正确 | 数据量大时每次都扫描全部 Feature |
| 只判断外接矩形 | 可能误判 | 较快 |
| 外接矩形粗筛 + 几何精筛 | 正确 | 只对候选点执行精确判断 |
| 服务端空间查询 | 正确且可扩展 | 需要 PostGIS 等后端能力 |

Polygon 的外接矩形会包含多边形之外的区域，Circle 的外接矩形四角也不在圆内，因此不能只做 extent 判断。

当前区域功能可以称为电子围栏的空间基础，但不是完整电子围栏。完整电子围栏还需要：

- 移动对象位置流；
- 进入、离开和停留判断；
- 边界抖动处理；
- 告警去重；
- 告警状态和处置闭环。

## 13. 为什么轨迹回放使用 requestAnimationFrame

当前轨迹点包含坐标和 Unix 毫秒时间戳。动画并不是每帧固定移动一个距离，而是根据真实经过时间和倍率计算目标轨迹时间，再在相邻采样点之间插值。

```ts
const ratio =
  (targetTimestamp - start.timestamp) /
  (end.timestamp - start.timestamp)
```

```ts
const coordinate = [
  startX + (endX - startX) * ratio,
  startY + (endY - startY) * ratio,
]
```

### 横向对比

| 方案 | 优点 | 局限 |
|---|---|---|
| setInterval | 使用简单 | 与浏览器绘制不同步，后台标签页和主线程阻塞会造成时间漂移 |
| requestAnimationFrame | 与浏览器绘制周期同步，更适合视觉动画 | 仍需根据真实时间计算进度，不能把帧数当时间 |
| CSS Animation | 浏览器优化较好 | 不适合动态修改 OpenLayers Geometry 和复杂时间轴控制 |
| Web Animations API | 控制能力较强 | 与 OpenLayers Feature Geometry 的集成不如主动更新直接 |
| 服务端轨迹流 | 可以展示实时位置 | 需要长连接和实时数据源，不是历史回放本身的实现方式 |

播放过程中复用人员 Point 和已巡 LineString，只更新 Geometry，避免每帧创建 Feature 和反复修改 Source。

## 14. 为什么使用 WGS84 和 Web Mercator 两套坐标

业务数据、GeoJSON 导入导出和接口参数使用 WGS84：

```text
[longitude, latitude]
```

OpenLayers 地图渲染默认使用 Web Mercator：

```text
[x, y]，单位近似为米
```

通过 `fromLonLat` 和 `toLonLat` 在业务层与地图层边界转换。

| 坐标体系 | 适用场景 | 特点 |
|---|---|---|
| WGS84 / EPSG:4326 | GPS、业务数据、GeoJSON、接口协议 | 使用经纬度，便于跨系统交换 |
| Web Mercator / EPSG:3857 | Web 地图瓦片和屏幕渲染 | 适合瓦片地图，但高纬度存在形变 |
| GCJ-02 | 国内互联网地图 | 相对 WGS84 存在偏移 |
| BD-09 | 百度地图 | 在 GCJ-02 基础上进一步转换 |
| 地方投影坐标系 | 测绘和高精度空间计算 | 需要明确 EPSG 和适用区域 |

当前使用天地图 `_w` 墨卡托瓦片服务，因此 WGS84 业务坐标与 Web Mercator 地图坐标可以通过 OpenLayers 标准方法转换。如果替换为高德或百度数据，必须额外处理 GCJ-02/BD-09 坐标偏移，不能直接混用。

## 15. 为什么使用 GeoJSON 导入导出

GeoJSON 是 GIS 系统中常见的开放交换格式，能够用 JSON 表示 Feature、Geometry 和 Properties。

项目导出的事件结构是 WGS84 Point FeatureCollection，不包含 OpenLayers Feature 等运行时对象。

| 格式 | 优点 | 局限 |
|---|---|---|
| GeoJSON | 可读、开放、前后端容易处理 | 文件较大，不适合超大数据量 |
| CSV | 简单、适合表格数据 | 空间几何表达能力弱 |
| Shapefile | GIS 工具支持广泛 | 多文件组成、编码和浏览器处理不方便 |
| KML | 适合 Google Earth 等场景 | XML 较冗长 |
| MVT 矢量瓦片 | 体积小，适合地图分片加载 | 不适合作为普通用户编辑后的完整业务交换文件 |

当前事件主要是 Point，GeoJSON 足够表达坐标和业务属性，也方便进行严格协议校验。

## 16. 为什么使用 shallowRef 和整体替换

事件集合可能包含大量普通对象。如果使用深层响应式，Vue 会递归代理对象属性，增加初始化和访问成本。

当前 Pinia 使用浅层状态，并在业务变化时替换数组和目标对象：

```ts
const nextEvents = [...events.value]
nextEvents[index] = updatedEvent
events.value = nextEvents
```

| 状态方式 | 优点 | 局限 |
|---|---|---|
| 深层 reactive | 修改对象属性即可触发更新 | 大集合会产生更多代理和依赖跟踪 |
| shallowRef + 整体替换 | 响应边界清晰，适合大列表 | 不能依赖内部属性直接修改触发更新 |
| Map/Set 原地修改 | 查找效率高 | 响应触发和序列化需要额外处理 |
| 将 Feature 放入状态库 | 地图操作直接 | OpenLayers 对象不适合业务状态库 |

完整十万条数据没有进入 Pinia；Pinia 只保存当前视口结果，进一步控制响应式成本。

## 17. 为什么列表还要分页

地图使用 Canvas 绘制 Feature，不会为每个点创建 DOM；事件列表则由 Vue 渲染真实 DOM。

即使地图能显示大量点，如果列表同时渲染数万行，仍会造成：

- 大量 DOM 节点；
- Vue VNode 创建成本；
- 布局和样式计算成本；
- 滚动卡顿。

当前每页最多渲染 100 行。

| 方案 | 优点 | 局限 |
|---|---|---|
| 普通分页 | 实现稳定，DOM 数量明确 | 翻页体验不如连续滚动 |
| 虚拟列表 | 可以展示连续长列表 | 动态高度、滚动定位和可访问性处理更复杂 |
| 无限滚动 | 移动端体验自然 | 已加载数据和 DOM 仍可能持续增长 |
| 一次渲染全部 | 实现最简单 | 不适合大量数据 |

当前项目选择分页，因为业务更接近任务管理后台，需要明确页码、首页、末页和目标页跳转。

## 18. 性能数据应该如何回答

当前源码确实记录了：

- 数据生成耗时；
- 空间索引构建耗时；
- 查询耗时；
- Feature 转换耗时；
- VectorSource 更新耗时；
- Feature Diff 耗时和增删改数量；
- 从数据更新到 `rendercomplete` 的耗时；
- 查询是否命中缓存；
- 当前地图 Feature 数量。

使用的主要 API 是：

```ts
performance.now()
map.on('rendercomplete', callback)
```

但是仓库中没有固化统一设备、浏览器版本和视口条件下的正式前后对比报告。

因此可以说“建立了性能测量点”和“采用了这些优化策略”，不能说“性能提升 60%”或“十万点稳定 60 FPS”。

推荐面试回答：

> 我先把耗时拆成数据生成、索引构建、空间查询、Feature 转换、Source 更新和 rendercomplete 六个阶段，通过 performance.now 和 OpenLayers rendercomplete 进行运行时观测。目前项目能够展示优化链路和实时指标，但没有在统一设备环境下形成正式 benchmark，因此我不会编造提升比例。

## 19. 为什么资源释放是 GIS 的重点

普通 Vue DOM 在组件卸载后通常由框架清理，但 OpenLayers 对象、自定义事件、动画和异步请求并不一定全部跟随组件自动释放。

当前卸载流程包含：

- 释放图片 Blob URL；
- 中止视口查询；
- 销毁查询 Controller；
- 清空完整 Mock 数据、空间索引和 LRU；
- 取消 `requestAnimationFrame`；
- 解绑 OpenLayers 监听器；
- 移除 Select、Draw 和 Modify；
- 移除 Overlay；
- 清空 VectorSource；
- 解除 ClusterSource 对事件 Source 的引用；
- 移除 Layer；
- `Map.setTarget(undefined)`。

### `setTarget(undefined)` 为什么不够

它只是解除 Map 与 DOM 的绑定，其他对象仍可能通过变量、Source、监听器或回调互相引用。因此必须按照对象所有权逐层释放。

## 20. 面试时必须主动说明的真实边界

1. 底图使用天地图 `vec_w + cva_w` 在线瓦片，需要浏览器端 Token 和域名白名单；它不是自建或政务内网地图服务。
2. 巡检事件使用固定 seed Mock 数据，不是真实接口数据。
3. IndexedDB 通用存储层正在开发，但尚未接入 GIS。
4. 当前固定网格索引运行在浏览器主线程，不是 PostGIS 或服务端空间索引。
5. 当前区域功能是空间圈选和管理，不包含完整越界告警。
6. 当前没有使用 Web Worker、WebGL Layer或矢量瓦片。
7. 已有运行时性能采集，但没有正式 benchmark，不能给出未经测量的性能提升比例。
8. 100k 表示完整 Mock 数据集规模，不代表地图会同时创建和绘制十万个 Feature。
